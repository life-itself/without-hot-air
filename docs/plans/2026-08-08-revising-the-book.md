# Revising the Book

**Written to be picked up cold.** A fresh session should be able to start from this
file alone — either to plan further, or to begin Phase 1.

**Goal:** bring MacKay's numbers up to date without pretending they are still his,
in a way a reader can see, and without wrecking the thing that makes this edition
useful in the first place.

**Tracking issue:** [#1](https://github.com/life-itself/without-hot-air/issues/1)

---

## Where things stand

- The book is 54 markdown files at the repo root, published by Flowershow at
  https://withouthotair.org
- The text is MacKay's 2008 text, **unmodified**. Tagged
  `text-as-converted-2026-08-08`
- Chapters carry frontmatter titles (generated by `extract.py titles`); figures
  live in `assets/`
- **The maths does not render** — [#3](https://github.com/life-itself/without-hot-air/issues/3).
  LaTeX was emitted without `$$` delimiters and shows as literal text across 14
  chapters. This is a conversion fault and blocks Phase 1: you cannot audit
  arithmetic you cannot read.

## The two things that make this edition worth anything

Every decision below should be tested against these. They are the product.

1. **It can be updated.** Not "is open source" in the abstract — visibly,
   continuously updated, by anyone, with the changes legible.
2. **The source is clean and reusable.** Someone can take this markdown and do
   their own thing with it. We did the tidying so they don't have to.

These pull against each other, and that tension is the central design problem
here: **the most obvious way to show changes is to mark them up in the text,
which is exactly what would ruin value #2.**

## Phase 2 — Decide how a change is shown

> **This one is Rufus's call, not an agent's.** Bring him the options and a
> recommendation; do not settle it and carry on. It is the decision every
> subsequent edit depends on, it is a product judgement rather than a technical
> one, and getting it wrong means redoing all of them. The recommendation below
> is a starting point for that conversation, not a resolution of it.

**Do not start Phase 3 before settling this.** Every edit made under the wrong
mechanism has to be redone.

The requirement: a reader sees, at a glance, what is MacKay's and what is ours —
"in red", or similar — while the markdown stays clean enough to reuse.

### Option A — Mark up the text

CriticMarkup (`{++added++}`, `{--removed--}`) or a custom `<Updated>` component
inline in the chapters.

*For:* explicit, authored, survives any renderer, easy to reason about per-edit.
*Against:* **breaks value #2.** Anyone reusing the markdown inherits our
annotation syntax. Also reintroduces the bare-brace hazard that
[#3](https://github.com/life-itself/without-hot-air/issues/3) is clearing up.

### Option B — Derive it from git *(recommended)*

Keep the markdown pristine. Diff each chapter against the baseline tag at build
time and render the changes as an overlay — a toggle, marginal notes, or coloured
inline spans.

*For:* serves **both** value points at once. Source stays clean and reusable; the
change history is exact, automatic, and free — it is already being recorded by
git whether we use it or not. No authoring burden, no syntax to learn, and it
cannot drift out of step with the text.
*Against:* needs build-time tooling that Flowershow does not have (see below).
Raw diffs are not automatically *readable* — a reworked paragraph diffs as a
whole-paragraph replacement, which is noisy. Probably needs a curated note per
change (a short "why") alongside the mechanical diff. Requires a stable baseline
ref, which is why the tag exists.

### Option C — Parallel texts

Keep `original/` and `revised/` copies side by side.

*For:* dead simple to diff and to explain.
*Against:* doubles the content, and they drift. A correction applied to one and
not the other is invisible until someone notices.

### Recommendation

**Option B**, with a per-change annotation file for the human-readable "why".
Mechanical diff for *what* changed, curated note for *why* — the diff is
generated, the reasoning is authored, and neither pollutes MacKay's text.

### The Flowershow question

Flowershow is a static markdown publisher. Option B wants build-time git access
and a custom rendering layer, which is outside what it does. Realistic paths:

1. Precompute the diffs into a data file, commit it, and render with an MDX
   component — stays within Flowershow
2. Move this site to a custom renderer (Next.js or similar) and keep Flowershow
   for the climate site
3. Extend Flowershow itself — it is Rufus's product, so a git-diff-aware feature
   is not out of the question

**Path 1 first.** It is much the cheapest, proves the UX is actually good before
anyone pays for infrastructure, and leaves both other paths open. Do not migrate
the site on a hunch that the UX will work — build the cheap version and look at it.

Whatever happens: **the book stays markdown.** That is not up for negotiation, it
is value #2.

**2026-08-08 correction to Path 1:** Flowershow has no mechanism to register a
custom React/MDX component — `<List>` and `<LineChart>` are its own built-ins,
not something this repo can add to. But Flowershow pages *do* render raw HTML,
inline `style=`, and even inline `<script>` directly in a `.md`/`.mdx` file (no
component registration needed) — the book's own text already relies on this for
`<span class="red">`/`<span class="green">` highlights. So "render with an MDX
component" was never viable, but "render with plain HTML in the page" already
is, no migration required. Path 1 is cheaper than the original framing assumed.

**One-page experiment built and reviewed 2026-08-08:** a mockup of chapter 6
with three of its audited claims (docs/audit.yaml) actually rewritten — panel
efficiency and the roof-PV arithmetic that depends on it, the PV-vs-market cost
comparison, and the world-PV-capacity comparison — shown with inline
strikethrough-original / highlighted-insert markup and a superscript link to a
dated, sourced "Updates" section, plus a three-way toggle (2008 original /
revised with changes shown / revised clean). Not deployed to the live site —
built and viewed as a standalone mockup per "build the cheap version and look
at it," using plain HTML/CSS/JS of the kind confirmed above to work directly in
a Flowershow page. Open finding from building it: MacKay's own text already
uses `span.red` to highlight important numbers (a different meaning), so an
"our updates are red" convention collides with his — the prototype uses a
separate amber/copper tone instead for that reason.

Standing constraints (also in `AGENTS.md`):

- **Never silently modernise.** MacKay cannot review these edits. Every change is
  visibly ours, dated and sourced.
- **Update the working, not just the answer.** The method is the value of this
  book; a changed figure with unchanged arithmetic is worse than useless.
- **Preserve his voice.** Where his framing still holds, leave it alone.

## Phase 4 — Then, and only then, launch

See [`docs/sharing.md`](https://github.com/life-itself/climate/blob/main/docs/sharing.md)

The short version: a new domain is not a story, but "we brought MacKay up to date
and here is how you can see exactly what changed" is. The 2021 post took 168
points; Goodall's 2017 *"someone should update this"* piece took 106. The appetite
is demonstrated. It is worth arriving with something built.

## Open questions for the next session

1. Annotate-only, or genuinely revise? Annotation is far less work and more
   honest; revision is more useful to a reader. Possibly annotate first.
2. What is the unit of change — a figure, a paragraph, a whole chapter?
3. Does a reader land on the 2008 text with updates layered on, or on the updated
   text with the original available? This is a real fork and shapes the UX.
4. How prominently should AI involvement be disclosed? It will be asked about.
   An asset if the method and sourcing are shown; a liability otherwise.
5. Is there a contributor path short of a pull request — could the "Edit this
   page" link carry a claim into the audit ledger instead?
